# 研究流程与跨版本交叉分析

本流程适用于research维护者；产品侧只消费已提交、已交付的规则、独立实现、数据与素材。
功能索引见[一代总览](dungeon_village_1/README.md)，样本与工具身份见[证据清单](dungeon_village_1/EVIDENCE.md)，
当前范围见[阶段交接](dungeon_village_1/stages/README.md)，实跑结果见[验证记录](dungeon_village_1/VERIFICATION.md)。

## 来源分工

| 输入 | 用途与边界 |
| --- | --- |
| 固定APK 1.0.8 | 当前规则、原表与既有回归的基线；它是汉化重签样本，不称为未经修改的官方包 |
| 用户提供的Windows安装目录`DungeonVillageEXE/` | 原版UI动态观察的优先入口，可直接运行检查布局、操作与动画；同时用语义名、资源、数据和消费者辅助交叉分析，不自动替换APK规则基线 |
| 用户截图／实况 | 记录画面与操作观察；版本未核实则保持未知，不自动归入APK或当前Windows样本 |
| 独立C++规则与研究原型 | 验证维护契约和组合行为；夹具、保护策略及黄金轨迹不是原程序动态证据 |

APK为Java／Dalvik与开罗Android框架；当前Windows样本为Unity 2021.3.11f1、x86 IL2CPP与开罗Unity适配层。
Windows应结合`GameAssembly.dll`和`global-metadata.dat`分析业务，不能只分析启动EXE。
Unity版本不是游戏版本；元数据名称、Java兼容层、同名方法和相同资源都不单独证明两版行为等价。

## 每批执行顺序

1. **核对现场与范围。** 检查工作区和最新维护交付，保留其他研究者在途修改。列出问题、来源、方案、取舍、
   预期交付与验收；已有确认沿用，新规则决策或实现范围变化先确认。按功能组织批次，不按每个方法拆阶段。
2. **固定输入。** 原始APK与Windows安装目录只读。APK记录包名、版本、签名和SHA-256；Windows记录文件相对路径、
   大小和SHA-256清单，登记引擎／架构／元数据版本，能取得时补Steam buildID／depot身份，缺失明确标未知。
   更新样本须作为新身份登记，不覆盖旧证据。工具版本、参数、输出哈希与定位方式一并记录。
3. **先复用已有证据。** 从功能规格和符号映射定位APK消费者，再用Windows语义名提出对应候选。
   APK巨型方法用低层指令交叉；Windows须先验证本样本的IL2CPP地址映射，再核对机器码与调用关系。
   dummy DLL仅辅助类型／签名定位，不当作方法实现；文件偏移、RVA、运行地址和元数据token分别标注。
4. **按问题做最小差分。** 依下表分别核对数据、代码、表现与时序。没有必要为每项APK小规则完整重做Windows研究；
   优先用于混淆语义、反编译歧义、视觉缺口和疑似版本差异，覆盖程度逐项登记。
5. **形成有边界的结论。** 区分两侧直接事实、局部控制流推断、跨版本对应假设、原型策略与夹具。
   Windows线索只有经APK侧核实，才能补充APK规则结论；仅有Windows证据的功能独立记录。
   发生冲突时保留两侧证据，暂停依赖该冲突的接入；先排查解析／定位错误，再区分版本、语言、平台或未知原因。
   已证独立工作继续；改换复刻目标或扩大范围须用户确认，不改原表或旧黄金值来消除差异。
6. **实现、验收与交接。** 确认范围内以独立C++表达已证契约，不复制反编译实现。批次实现完成后集中整理测试，
   按[现行构建约定](dungeon_village_1/README.md#构建缓存管理)执行单Release标准及按风险选取的长测；
   原程序动态观察、研究窗口、OS输入与产品验收分别记录。仅流程文档修改检查差异、链接和约定一致性，
   不触发游戏回归。同步功能规格、证据、阶段与验证记录后，只提交本批已核对内容，不自动推送。

## Windows交叉分析的检查层次

| 层次 | 需要核对 | 可以得出的结论与限制 |
| --- | --- | --- |
| 结构与命名 | PE／IL2CPP身份、类型／方法签名、调用定位 | 建立符号对应候选；名称相似不等于实现相同 |
| 数据与素材 | Unity对象／条目身份、原始与解码后哈希；表格按ID、行序、列逐项比较，语言字段单列 | 只认证实际比较的字节或字段；同表不证明消费者语义，同图不证明动画绑定 |
| 方法与业务 | 两侧条件、数值类型、取整／溢出、状态读写、随机抽取及调用顺序 | 认证指定方法／路径范围；反编译警告、优化与未解析调用保持未知，不外推全系统 |
| 框架与动态 | 新局／存档条件、命令顺序、速度／暂停、输入、更新／绘制资格、窗口尺寸与语言 | 记录真实程序的观察及运行环境；一侧实跑不等于双侧轨迹一致，截图不认证持续时序 |

初次验证Windows方法工具链可优先选择已有APK合同的地图扩张、一个收费／道具消费者、更新与随机入口。
已有资产差分只复用已登记的覆盖范围；未比较条目保持待验证。APK的47ms观察、Java48随机、页码与逻辑tick
都要经Windows真实消费者重新核实，不能直接套用；不能用研究原型的运行速度替代原程序时钟。
比较动态轨迹时先说明可控制与不可控制的初态／随机条件，无法对齐则报告局部观察，不强行声称逐帧一致。

## 优先运行Windows版研究UI

Windows版可在当前桌面环境直接运行，是菜单、布局、动画与真实输入研究的重要优势。
UI研究优先通过实际操作建立观察，再按需结合资源与方法定位；不必等待完整IL2CPP业务反编译才开始观察。

1. 记录本次安装样本身份、语言、窗口／全屏状态、客户区尺寸、系统DPI／游戏缩放、新局或存档条件。
2. 围绕具体操作链运行原游戏，如菜单→建设→放置／取消、人物→详情→返回、任务接受→征集→结果。
   记录鼠标／键盘动作、页面切换、按钮启用条件、选中／悬停反馈、滚动和弹窗遮挡；暂停及关闭后的行为单列。
3. 布局用截图标注相对锚点、尺寸、层级、文本和资源候选；动画、过渡、计数显示与输入反馈用录像或带时间顺序的观察记录。
   单帧只证明该帧可见内容，录像时长不直接换算逻辑tick。需要检查模拟是否暂停时，另记录可观察的世界状态变化。
4. 截图／录像与操作记录在现有[视觉参考](dungeon_village_1/references/README.md)中按来源归档，登记日期、样本、
   复现条件、文件哈希及尺寸；不将旧的未知版本截图追认为本次样本。只记录实际完成的观察，失败与未覆盖路径明确保留。
5. 将Windows实测的布局、动画和输入事实映射到[UI规格](dungeon_village_1/ui/README.md)，
   再核对APK页面生命周期、资源绑定与规则消费者。相同／不同／未知分别交付；Windows特有布局或操作可作为产品候选，
   涉及改变已确认的复刻目标或交互方案时另行确认。APK缺少动态证据时，Windows观察仍是有效的独立UI交付，标明适用版本即可。

## 差分记录与交付

每项记录保留以下最小字段，放入对应功能规格的交叉分析段或现有验证报告，不为每个方法新建文档：

| 字段 | 内容 |
| --- | --- |
| 问题与范围 | 要验证的具体行为，以及未覆盖的分支／条目 |
| APK证据 | 固定样本身份、条目／符号、工具版本与定位、直接事实或推断 |
| Windows证据 | 样本清单身份、资源对象／条目或模块＋地址／签名、工具与定位、证据等级 |
| 比较条件与结果 | 输入／语言／操作／随机条件；字节一致、字段一致、指定行为一致、差异或未知 |
| 影响与下一步 | 是否可补充APK合同、是否仅属Windows、依赖缺口与最小后续核对 |
| 验证状态 | 静态核对、原APK实跑、原Windows实跑、独立C++回归分别列出日期／结果；未运行写待验证 |

证据索引集中维护身份与工具；功能正文维护语义与差异；阶段文档维护范围和决策；验证文档维护实际检查。
“Windows上跑过C++测试”与“原Windows游戏已动态验证”必须明确区分。
生成Java、IL2CPP映射／反编译输出、提取中间文件及技术探针放忽略的`dungeon_village_1/work/`，
不混入维护实现。原程序不提交；交付数据／素材另登记所属版本、原路径／对象、哈希、尺寸、转换和用途，
两版资源不无标记覆盖；产品运行不读取原程序或work。

2026-10-06用户确认引入Windows制品交叉分析；本次仅整理流程，不变更固定APK基线或新增动态认证。
若未来改以Windows版为目标，须另行确认范围、建立该版合同与验收，再按功能迁移；现有APK证据继续保留。
