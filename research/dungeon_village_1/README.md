## 构建缓存管理

研究构建与验收缓存只放在本项目被忽略的[work目录](work/)，不再向系统临时目录创建构建树。
用户已确认日常使用[研究聚合入口](CMakeLists.txt)，只保留`work/release`这一套Release构建树；
不再要求每批三包分别进行Debug与Release六套验收。Debug仅在定位问题时按需配置`work/debug`，
完成后收齐进程并清理；专项插桩也只在`work`下建立有职责名称的目录，不按轮次无限新增副本。
三包独立CMake入口保留用于依赖边界检查或独立使用，不常驻重复缓存。聚合入口只定义一份领域库；
prototype包含的87项领域测试只注册一次，加上35项原型测试及5项工具测试，共127项唯一标准测试。
2026-10-10用户明确由产品侧承担世界长跑，研究侧只做本批受影响的最小功能／逻辑测试，优先在现有套件中用`ctest -R <相关用例>`选择；不再默认全套标准CTest或`long-world`，不以自然逐星／通关为研究交付前置。
既有测试注册、有效断言及历史快照／证书保留；存取变更可做必要短恢复测试，纯文档／静态研究只核来源与文档。完整分工见[研究流程](../WORKFLOW.md#研究与产品的测试分工)。
本地Release与按需Debug均默认`BUILD_SHARED_LIBS=ON`；同一构建树的`bin/`共置可执行程序和运行DLL，
`lib/`保存导入库／静态归档，不再让每个测试重复嵌入完整世界库。Windows运行库按目标架构定位，
原型使用项目内`work/local-tools/raylib-shared`的动态raylib；只有另行向玩家分发的Release制品才显式配置静态例外。
不同构建树不共写同一个DLL目录；按需Debug使用自己的匹配库，不混用Release DLL。
旧缓存`-static`必须在进程收齐后显式清空；具体参数与DLL边界见[原型构建说明](prototype/README.md)。
阶段结束先收齐进程，再按CMake源目录核对后清理已废弃的构建/专项缓存；当前可运行原型保留。
`work/decompiled`、分析证据与尚在使用的输出不当作构建缓存整树删除；源码、原表、素材不参与缓存清理。
迁移批123项标准及窗口验收通过，六个旧缓存已清理；最新25分区审计批127项标准通过，`work/release`约86.80MiB；
全过程与体积范围见[验证记录](VERIFICATION.md)，不能靠保留旧构建日志代替当前回归。

## 复现静态分析

从仓库根目录执行，需本地 APK 和 JADX 1.5.6：

```sh
jadx --show-bad-code --comments-level warn \
  --output-dir research/dungeon_village_1/work/decompiled \
  research/dungeon_village_1/maoxianmigongcun.apk
```

生成 Java 和调用图只在忽略的工作目录中，不加入维护源码。更换反编译参数可能改变行号，
不得用带重构警告的输出认证完整分支顺序。各包的独立构建方式及当前结果见 [验证入口](VERIFICATION.md)。
