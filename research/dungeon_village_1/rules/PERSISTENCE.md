# 存档与恢复

## 范围与结论

本文只分析[固定 APK 的身份](../EVIDENCE.md#输入与工具)，不把异版本截图或当前 C++ 内存检查点当作原版存档。
依据为已有 JADX 1.5.6 生成源码；本批没有读取设备上的真实存档、运行 APK、修改 APK 或实现其格式。
普通输出中运行时加载大方法有大量重复／控制流警告，因此分区字段与小方法可直接定位，
加载后的迁移／修复大分支仅登记已见调用，不认证全部分支顺序和版本兼容性。

已能闭合的关键结论：

- 两个存档栏各自有手动数据和“中断数据”，不是一个最新快照反复覆盖全部用途。
- 实际 Android 持久介质是 Activity 私有 `SharedPreferences` 字符串记录。
  外层是 Base64；解码后为共同 XOR 处理的“8 字节校验值＋容器”。不是直接把 Java 对象序列化进文件。
- 手动保存由 `raw14` 执行；自动保存由日历即将跨越 `10800` 的逻辑进度触发，并保存跨界前的旧进度。
- 定义共享成长、人物／怪物、设施、任务、遭遇、物体、投射物、地图和延迟脚本续体都有明确保存分区。
- 共同游戏随机对象的 seed／游标没有持久化。载入游戏不恢复它，也不以固定 seed 重建它。
- 页面栈、页面局部计数／选择／问答及全局通知／浮标队列不保存；世界实体动作计数与物体／投射物进度却会保存。
  “动画不保存”不能概括两者。
- 原加载过程先重置并直接修改全局世界；它不是当前维护 C++ 使用的候选 Owner 成功后替换事务。

当前成果是来源规格和可执行的下一批方向，不是“正常文件存取已经完成”。

## 存储槽与系统索引

原 `kairo.android.c.e` 以存储组号和三位补零索引拼记录键。游戏状态使用组 `0`；
组 `1` 另用于 APK 资源，不能把资源归档和玩家存档混成同一输入。

| 字符串键 | 记录用途 | 选择方式 |
| --- | --- | --- |
| `0000` | 系统 `J` 容器 | `d.a.c()` 读，`d.a.d()` 写 |
| `0001` | 第 1 栏手动游戏 `P` | `aP=0`、`a(false)` |
| `0002` | 第 2 栏手动游戏 `P` | `aP=1`、`a(false)` |
| `0003` | 第 1 栏中断游戏 `P` | `aP=0`、`a(true)` |
| `0004` | 第 2 栏中断游戏 `P` | `aP=1`、`a(true)` |

保存先提交选定游戏记录，再更新系统目录中的日期、资金字符串和村名，最后调用系统写入。
日期目录值是 `year*10000+month*100+week`，三者仍为原零基字段；栏位显示再加一。
手动日期在 `J.int[6+aP]`，中断日期在 `J.int[11+aP]`；村名分别在 `J.string[2+aP]`／`[6+aP]`，
资金分别在 `[4+aP]`／`[8+aP]`。当前选择栏位存 `J.int[8]`。

标题页用目录日期 `-1` 判断没有数据，不先扫描游戏记录验证有效性。
“删除存档”在已见输入分支只将对应目录日期置 `-1` 后写系统，并未擦除对应游戏记录。
因此它是目录不可见化，不能作为敏感数据擦除保证。

`e.a()` 还有把旧 `openFileInput` 文件逐一迁入偏好字符串、提交后删除旧文件的路径；
运行时协调器首次初始化调用它。它不等于当前 APK 常规保存仍以 `save1.dat`／`save2.dat` 写文件。
未取得真实设备 XML，偏好文件的实际完整路径不在本批认证范围。

## 保存与载入时点

### 手动保存

主场景的保存命令及菜单保存命令均创建 `raw14`。
页面初始化显示“游戏保存中”，其更新先将 `ce=0` 改为 `1`，下一次更新调用 `av.e()`，
后者固定转 `a(false)`；完成／失败后 `ce=2`，等待确认返回。
不能在 UI 绘制回调、每帧或打开菜单时重复提交保存。

页面失败时显示 `保存失败【bG】` 和异常，附加至系统诊断字符串并截取最后 1024 字符，尝试再保存系统。
`bG` 是分区写入阶段诊断，不是持久化 schema 版本。

### 自动“中断数据”

日期推进先将当前 `P.int[4]` 留到 `[5]`，加本轮推进量；若结果达到 `10800`，
暂时将 `[4]` 恢复为旧值，执行 `a(true)`，再恢复新增值并开始周／月／年归一化与结算。
即保存的是本次跨周日历消费者之前的状态，不是跨月维护费和事件全部完成之后。
`10800` 是原逻辑进度边界，不擅自换算成秒，也不描述成仅“每月自动保存”。
保存程序先设 `P.int[15]=1`，手动和自动都如此。

已见 Android 生命周期 [IApplication.java](../work/decompiled/sources/kairo/android/ui/IApplication.java)
的 `onPause`／`onStop`／`onDestroy` 没有调用游戏保存，最后一项直接结束进程。
全游戏调用核对只找到日历的直接 `a(true)` 和手动 `e()->a(false)`。
因此不能宣称失焦、切后台或系统终止必然保存到最近一轮。

### 载入

标题页选择“从中断数据处开始”或“读取存档”；前者直接调用加载，后者经过继续／重新开始／删除菜单。
实际加载入口使用 `a(slot, use_interrupt)`，偏好记录索引仍为 `(use_interrupt?3:1)+slot`。
进入加载前先调用新局重置入口并更新当前栏位及系统记录，之后读 `P` 和各分区；成功切入主场景。
主场景初始化重建普通状态 `0`、菜单页和自己的临时向量，不恢复保存时原页面栈。
加载失败标题页清 `P` 并显示“读取失败”，不是回滚到载入前正在游玩的世界。

## 二进制层级与边界

### 记录外壳

写入顺序是 `P.a()` 容器字节→原游戏校验→前置 8 字节大端 long 校验值→共同 XOR→标准字母表 Base64→偏好字符串 `commit()`。
读取反向处理，空／不存在记录返回空字节；非空记录去掉 8 字节头并核对校验，失败抛游戏异常。
XOR 密钥由协调器初始化的 11 个 int 拆为 44 字节，拆字节按低位到高位；不来自随机流。
这是可逆格式处理，不是可靠的加密或认证。

校验不是标准 CRC-32：原表生成的多项式分支与标准 CRC 相反。
现有[归档工具](../tools/src/archive.cpp)的 `game_crc32` 已独立维护该差异，不能调用标准 `crc32` 冒充。
偏好 Base64 解码器支持 GZIP 头，但本 APK 的正常偏好写入不先 GZIP；不要替所有保存负载假定压缩。

### `k` 容器

每个容器开头写大端 `int32` 组数 `5`，随后每组依次写 `int32 tag`、`int32 count` 和组内容：

| tag | 内容 | 单项表示 |
| --- | --- | --- |
| 0 | 子容器数组 | `int32` 字节长度＋子容器字节 |
| 1 | int 数组 | 大端有符号 32 位 |
| 2 | long 数组 | 大端有符号 64 位 |
| 3 | 字符串数组 | `int32` 字节长度＋字符串字节；写端 `getBytes()`，没有显式记录字符集 |
| 4 | 原始字节数组分区 | `int32` 字节长度＋原始内容 |

游戏根 `P` 的默认形状是 1 子容器、16 int、3 long、1 string、25 字节分区；
系统根 `J` 默认是 0 子容器、16 int、4 long、12 string、4 字节分区。
游戏的资金在 `P.long[0]`，日历在 `P.int[1..5]`，村名在 `P.string[0]`。
`P.child[0].int` 在写前指向固定事件调用计数 `aM`。

基础流还使用大端 `int16`、单字节布尔值及 `float` 的 IEEE-754 原位 `int32` 编码；
三维向量为三个 float，不能把人物或摄像坐标保存为整数地图格。

这些类型读器会在请求长度不足时抛 EOF，但没有已见全局最大计数／负长度／剩余尾字节／重复 tag 严格验证。
容器对预先存在的 int／long 等数组读取输入全部项，仅写入目标长度以内；短输入保留默认尾部。
子容器循环则先索引原子容器再作范围判断，不能由此推导任意长度安全。
多个固定目录分区按已加载定义表长度循环，没有每条定义 ID 或分区内记录数；地图按已建地图大小循环。
因此目录版本、尺寸和向量有序性属于隐式依赖，不是通用可扩展文件协议。

## 实例与引用恢复

### 设施

[c/m.java](../work/decompiled/sources/c/m.java) 223／279 的读写保存原全局实例 ID、同定义序号、定义索引、
生命周期／计数、可变历史、锚点、朝向、关联人物定义、月度经营等。
使用者是人物 UID，写器不序列化 Java 引用；读器先保存 UID 数组 `A`，第二阶段 `a()` 在 `bl` 中逐项查回。
未找到使用者时打印 `Tenant.java deserialize2()` 诊断并缺少该引用，并非整个原存档统一拒绝。
原生成读器还消费设施 `p` 的效果对却没有向该向量追加；本批没有低层交叉，不把它宣传为完整效果队列恢复已证。

地图读取会根据静态格定义先重新创建设施，随后分区 24 按保存锚点匹配新建实例并读完整记录，
最后才恢复使用者和任务引用。分区 22 再补定义／位置匹配的朝向。
加载器此段有控制流警告，精确重建／清理分支仍应以低层或真实存档样本交叉，不能直接翻译大方法。

### 人物、怪物、遭遇和任务

小型第二阶段方法已直接可读：

| 保存引用 | 读取暂存 | 第二阶段解析 |
| --- | --- | --- |
| 人物 `R`、怪物 `S`、遭遇 `db` | `c.b.aC/aD/aE` | [c/b.java](../work/decompiled/sources/c/b.java) 4135，在 `bl/bm/bn` 中按原 UID 查；`dc` 由遭遇战斗组派生 |
| 遭遇目标及双方成员 | `c.f.t`、战斗组 `i/j` 数组 | [c/f.java](../work/decompiled/sources/c/f.java) 178，双方按 `bl/bm` 查回，不创建替代成员 |
| 投射物来源／目标 | `c.j.o/p` | [c/j.java](../work/decompiled/sources/c/j.java) 119，按 `bl/bm` 查回 |
| 任务绑定设施／遭遇 | `c.k.k/l` | [c/k.java](../work/decompiled/sources/c/k.java) 210，按设施原 ID／遭遇原 ID 查回 |
| 活动任务／参与者 | `UserData.P/Q` | [c/n.java](../work/decompiled/sources/c/n.java) 3121，任务按实例 ID 查回，参与者保留人物定义 ID |

已见协调器重建序为先读实时实体／物体／遭遇／投射物／任务，再读全局和地图／设施，
随后人物→怪物→遭遇→投射物→任务→设施→`UserData.b()` 的第二阶段引用恢复。
最后的 `UserData.b()` 还会移除已在出口且满足 flags512／1024 的人物，加载并非纯字节还原。
共同地图／邻接／渲染刷新另在加载尾部执行。

原 UID、人物定义 ID、设施同定义序号和维护 C++ 稳定 ID 不是一个身份空间。
原作者有首空槽分配策略，维护代码单调稳定 ID 则为了退休对象可达性；存取不能丢掉这一区分。
有些投射物／遭遇目标以 short 写 UID，而人物主体 UID 为 int；不擅自补成所有源 UID 永不溢出的保证。

## 脚本、页面、动画与随机

### 延迟续体保留，页面执行栈不保留

[c/c.java](../work/decompiled/sources/c/c.java) 的续体只在脚本 opcode6 产生。
程序身份由当前目录引用匹配：普通固定事件 `0+index`、人气程序 `1000+index`、设施程序 `2000+index`；
保存下一条指令和等待值，重载后主场景逐项减等待，到零恢复 `P.int[9]` 并从原位置继续。
它不是当前 C++ 的全部立即执行调用栈、页面栈或一般回调根的原字节表示。

原 [kairo/android/a/b.java](../work/decompiled/sources/kairo/android/a/b.java) 的页面 `f384b` 没有保存入口，
25 分区写器也不写任何 `b.g`；`raw14` 自身不会被保存后重开。
当前输入、选中行、已打开详情／问答／征集页面、页面局部计数和一次性声音均不能宣称可精确续演。
如果已创建未关闭成果页，其领域奖励及任务状态可能已保存，而结果页本身没有；
必须据原实际触发范围另验是否会遗漏或重放，不能从“世界有存档”自动推得“任何页面可保存”。

### 世界动作和表现记录分别对待

人物控制 FIFO `m`、连续坐标 `n/o/p/q/r`、格／投影缓存 `s/t/u/v`、状态 `A` 和动作计数 `B` 等确实写入。
物体阶段、投射物计数也写入。因此行走／战斗／旅馆服务不全部重新起步。
但人物 `cd/ce` 等局部显示队列，以及协调器 `S/X/Y` 通知／浮标／延迟特效向量未在写器中保存，
新局重置入口明确将 `S/X/Y` 设为空。摄像只写三个向量，不保存所有跟随引用。
当前 C++ 的表现缓存保存政策应分别记录“原来源已保存”与“维护为了检查点保留”，不能一律删或一律序列化指针。

### 原随机 seed／游标不保存

共同游戏随机只有 [c/d.java](../work/decompiled/sources/c/d.java) 的 `private static Random r=new Random()`，
抽取为 `abs(nextInt()%bound)`。全生成源码搜索未见它的 setter、反射访问、Java 对象序列化或 seed 导出／恢复，
完整保存写器也没有它的分区。

结论限定到这个固定 APK：同一进程载入会延用当前 `Random` 的已消费状态；
冷启动由 Java 默认构造生成新的 seed，不能保证从同一存档继续得到同一条随机轨迹。
原标题动画也消费共同随机，所以“先停在标题多久”可能影响后续流。
`Random` 自身的内部状态不是已见保存在 `UserData` 某个未命名 int 中的字段。

维护 C++ 当前有明确 Java48 seed／原始磁带和消费游标。为了可复现测试保存该状态是有价值的独立策略，
但不得标成原 APK 已保存 seed，更不能用原默认 seed 未知来填固定 `1` 后宣称原版复演。

## 版本与失败策略

系统默认 `J.int[0]=108`，启动加载器遇到小于108会写回108。
此处只见系统版本标记更新；游戏根默认 `P.int[0]=0`，本次没有找到载入游戏前对 `P` schema 版本严格相等的检查。
网络响应“版本大于108”的检查是客户端／网络认证路径，不是本地存档 schema 校验。
不由这些字面量推导跨版本存档普遍兼容，更不复制原修复大分支作为维护旧档迁移功能。

原存取风险必须与维护策略分开：

- 偏好 `commit()` 返回失败会抛异常，但游戏记录与系统目录分两次提交，没有跨记录原子事务。
  游戏已提交、系统未提交时目录可能落后；系统写器 `d()` 自己捕获异常并打印，手动页不一定收到该错误。
- 序列化先修改 `P` 标志和字节分区，保存失败没有已见候选快照回滚。
- 加载先重置当前世界和系统选择，再逐分区修改；缺引用在多个小方法中置空／省略，不全是加载错误。
- 外壳校验只检测字节改动；不会检查业务 UID 唯一性、地图占地、目录 ID、重复成员、负尺寸或资源配额。
- 原格式字段宽度和目录隐式长度构成约束，不能因 C++ 容器支持更大规模就声称原格式也支持。

## 当前 C++ 边界与下一批

[唯一研究 Owner](../prototype/include/dungeon_village_prototype/startup_world_runtime.hpp)和
[阶段检查点](../prototype/src/startup_world_runtime.cpp)目前只有完整不可变内存副本，不写玩家文件。
`StartupWorldRuntimeSession::checkpoints_` 每次成功跨界追加一份完整世界，没有已见容量上限；
资源规模检查应计入这类审计缓存，不将它当作正常两栏自动存档的必需历史。
静态 `rules` 指针、执行期引用、raylib 资源、临时投影与输入快照不应作为对象内存直接转储。

### 最小可实施方向（维护建议，尚未实现）

先做当前研究 schema 的存取，不实现读原 APK 档，不做旧 demo 档迁移：

1. 定义有界、可版本拒绝的 `SaveSnapshot`：固定数据集身份、维护 schema 版本、唯一 Owner 的耐久字段和身份映射。
   从原分区表列字段覆盖表，未解释但已维护字段按 `legacy_*` 保留，不遗漏共享定义成长或改名／住宅数据。
2. 确定最小安全保存入口为无页面事务中途的稳定主场景，并显式拒绝暂不支持的模态状态。
   该约束是首版维护范围，不是原版所有页面自动保存资格。
   之后若要完整恢复征集／授勋／结果页，扩展 schema 保存维护页身份／父引用／阶段及续体，不能仅保存 raw 页码后重初始化。
3. 同一逻辑事务边界捕获快照，持久化 seed／游标以做确定性验收；原进程随机延用政策另记，不混成一个承诺。
4. 文件层写同目录临时文件，完整 flush／校验后原子替换，自动和手动目标分开；
   失败保留上一个成功文件与当前 Owner，报告明确错误，不继续写“保存完毕”。
5. 读取为候选快照，先校验字节边界和预算，再按稳定 ID 建表／恢复引用／重建地图与派生缓存，
   全部成功才替换当前 Owner。目录哈希／版本未知、重复ID、悬空耐久引用或占地冲突应拒绝，不能补新人物兜底。
6. 加入资源规模观测：档大小、实体／退休可达对象数量、续体／页面数量、审计检查点数量、读取分配总量；
   明确哪类合法历史会增长、哪类短期输出应消费，避免通过存取把无引用对象永久累积。

初版接口只需职责清楚的“捕获快照／验证并重建候选／读写文件”，不预建存储服务容器或统一事件总线。
跨平台原子替换和持久化级别属于接入层设计，C++17 核心不要依赖 Android `SharedPreferences`。
具体格式选择、任意模态恢复范围和写入权限仍需该存取批次设计确认；本研究只提供原依据与风险。

### 验收合同

| 层 | 应验合同 |
| --- | --- |
| 字节层 | 截断／超长／负长度／溢出／重复段／尾字节、版本与数据集拒绝；每层资源预算有效 |
| 领域覆盖 | 住宅、装备、职业成长、设施共享升级、改良、现金／日期／报表、任务与延迟续体可往返 |
| 恢复事务 | UID 与稳定 ID 不混淆，地图／占用／目标重建，非法引用拒绝；失败当前 Owner 与旧档都不变 |
| 次序与随机 | 取快照不推进世界、不抽随机；恢复后同输入轨迹与未退出基线比较，维护随机契约明确 |
| 业务风险 | 到达已收费但仍在使用、施工中、战斗／投射物、任务自然成功前后、跨月前检查点、不重复奖励／维护费 |
| 页面边界 | 暂不支持的页态明确拒绝；支持后不重复初始化／授勋／升级，held 输入不跨进程恢复为按住 |
| 文件失败 | 写途中失败／损坏候选／系统目录不同步，恢复旧成功档；实际平台文件权限与替换行为另验 |
| 长期规模 | 重复保存／载入／任务周期后临时队列和检查点不无限增长；合法统计增长另记 |

测试优先扩展现有共享 Owner、任务、建设与随机职责套件；字节格式／文件隔离才建立独立持久化套件。
不为存档再复制一套战斗或建设算法作为夹具，也不把 C++ 往返通过写成原 APK 字节兼容已认证。

## 仍需补的证据

- 至少一份真实设备手动与中断记录样本，交叉校验外壳、字符串编码、容器尺寸、地图与分区终点。
- 运行时加载巨型方法的低层交叉：不同记录大小、完整设施锚点匹配、旧格式／不合法地图修复分支及引用次序。
- 自动存档期间是否可能存在特定页面／成果奖励未确认状态，以及冷启动后是否会漏提示或重新触发。
- 原设施效果队列 `p` 的读后保留行为；不因写器有该项就假设读器完整恢复。
- 原档超过 short UID／计数、动态对象退休、目录增长和读取预算的实际边界。

这些缺口不阻碍按独立 schema 制作“当前版本、主场景稳定点”的 C++ 存取原型，
但阻止宣称任意原 APK 存档兼容、任意页态续演或原版确定性重放完成。
