# 存档与恢复

## 范围与结论

本文以[固定 APK 的身份](../EVIDENCE.md#输入与工具)为规则基线；Steam交叉证据单列，不把异版本截图或当前 C++ 内存检查点当作原版存档。
依据为 JADX 1.5.6 普通／低层源码及2026-10-07补充的Steam机器码；已只读分析用户提供的Steam系统／手动／中断记录，
尚无固定APK设备档；已消费用户另会话的Steam真实恢复实验，本研究分析会话只读冻结证据，不修改原档。
未实现原档导入维护Owner。实际动态覆盖见[历史验收](../verification/PERSISTENCE_HISTORY.md)，平台差异单列。
普通输出中运行时加载大方法有大量重复／控制流警告，因此分区字段与小方法可直接定位，
加载后的迁移／修复大分支仅认证下文已核对路径，不认证全部分支和版本兼容性。

已能闭合的关键结论：

- 两个存档栏各自有手动数据和“中断数据”，不是一个最新快照反复覆盖全部用途。
- 实际 Android 持久介质是 Activity 私有 `SharedPreferences` 字符串记录。
  外层是 Base64；解码后为共同 XOR 处理的“8 字节校验值＋容器”。不是直接把 Java 对象序列化进文件。
- 手动保存由 `raw14` 执行；自动保存由日历即将跨越 `10800` 的逻辑进度触发，并保存跨界前的旧进度。
- 定义共享成长、人物／怪物、设施、任务、遭遇、物体、投射物、地图和延迟脚本续体都有明确保存分区。
- 共同游戏随机对象的 seed／游标没有持久化。载入游戏不恢复它，也不以固定 seed 重建它。
- 页面栈、页面局部计数／选择／问答及全局通知／浮标队列不保存；世界实体动作计数与物体／投射物进度却会保存。
  “动画不保存”不能概括两者。
- 原加载过程先重置并直接修改全局世界；它不是当前维护 C++ 使用的候选 Owner 成功后替换事务。

原版来源分析与维护实现分开：2026-10-07已按用户继续授权实现独立维护文件格式与恢复接口，
模块范围见[文件存取与回放](../prototype/PERSISTENCE.md)，本批验收结果见[验证记录](../VERIFICATION.md)。这不等于原APK／Steam档兼容。

缩小每批长测范围、针对中后期场景采样、设计可校验的测试快照以从中途重复回放；

本节保留用户要求及持续约束，**不是原版事实**。维护正常文件与晋级精确回放已实施验收，
当前支持范围见[维护模块](../prototype/PERSISTENCE.md)，其它快照资格与剩余原档证据见[阶段矩阵](../stages/README.md#存档能力判断)。

### 测试提效要求

- 根据本批改动选择相关长链，保留必要的新局端到端验证；不机械重跑全部长测，也不删除有效断言。
- 性能采样覆盖中后期人物、任务、账本和审计历史规模，不能只用早期3000步结果代表全部世界。
- 中途回放快照必须来自有来源记录的合法轨迹，登记输入／定义哈希、快照格式、原种子、已消费命令位置和状态摘要。
  恢复后执行相同后续命令，须与不中断运行的尾段核对资金、随机、日期、实体／引用、页面及一次性输出。
- 快照登记生成实现版本，但复用资格按输入与状态语义兼容性判断，不能每次实现提交变化就机械全部重建。
  若改动影响生成快照的前缀规则或状态含义，则标记失效并重建；格式演进和兼容策略在独立设计中明确。
- 快照恢复是加速重复验收的设施，不是向自然路径注入人气、日期或奖励；从新局自然可达与快照恢复后正确继续分别验收。

### 三种对象分别设计

| 对象 | 目标与边界 |
| --- | --- |
| 原APK存档模块 | 继续补齐25分区、嵌套结构、读取／写入、引用恢复和失败分支的来源分析；目前仍缺真实存档及完整加载大分支认证 |
| 研究正常文件存取 | 已实现稳定主场景维护格式；保持唯一Owner，文件写入失败保留旧有效档，加载失败返回错误且不替换当前世界；具体验收另记 |

捕获／恢复必须选择明确的事务边界；若支持轮内位置，还必须保存恢复阶段，避免重复此前AI、收费或日历消费者。
具体使用独立测试格式、扩展分区还是伴随数据，由独立设计决定，不把这些维护策略写成APK原格式。

### 未实现字段的保留原则与持续可用门槛

- 先明确容器、类型、长度、字段边界及引用关系，再决定哪些字段暂不解释业务语义。
  独立未知载荷可以作为不透明数据保留并原样往返；“占位”不意味着补零、丢弃或臆造原初值。
- 涉及身份、实体引用、计数、校验或后续消费者的字段不能盲跳；若修改已知状态会破坏不透明部分的引用，
  必须解决映射或明确拒绝该不支持操作，不能报告成功却保存损坏关系。没有原始载荷的新局字段也不能伪造字节。
- 将存读档往返及恢复后继续运行设为后续功能批次的持续回归门槛；新增持久状态同时维护读写／校验／回归。
  新功能不能把保存／读取长期搁置到全部玩法实现之后；能保留的不透明字段不因暂未实现其功能而丢失，格式版本和能力范围显式登记。
- “永远可用”落实为已声明支持范围内的长期能力和失败安全：无静默丢状态、不损坏旧有效档、不部分替换世界，
  对损坏文件、不支持版本和介质错误给出明确结果，而不是承诺任意输入、任意I/O故障都能成功。

2026-10-07已完成来源补充、容器保留与Session分叉短探针，具体下一批方案见[快照恢复与重复回放设计](../stages/PERSISTENCE_REPLAY.md)。
随后用户授权继续完成，首版选独立维护格式，不导入原APK／Steam档，不做旧档迁移；已知长度且不影响引用的可选附属段可原样保留。
此前“不做旧档迁移”不自动改为无限兼容承诺；正常存取与精确测试恢复共同规划，验收等级分别记录。

## 存储槽与系统索引

原 `kairo.android.c.e` 以存储组号和三位补零索引拼记录键。游戏状态使用组 `0`；
组 `1` 另用于 APK 资源，不能把资源归档和玩家存档混成同一输入。

| 字符串键 | 记录用途 | 选择方式 |
| --- | --- | --- |
| `0000` | 系统 `J` 容器 | `d.a.c()` 读，`d.a.d()` 写 |
| `0001` | 第 1 栏手动游戏 `P` | `aP=0`、`a(false)` |
| `0002` | 第 2 栏手动游戏 `P` | `aP=1`、`a(false)` |
| `0003` | 第 1 栏中断游戏 `P` | `aP=0`、`a(true)` |
| `0004` | 第 2 栏中断游戏 `P` | `aP=1`、`a(true)` |

保存先提交选定游戏记录，再更新系统目录中的日期、资金字符串和村名，最后调用系统写入。
日期目录值是 `year*10000+month*100+week`，三者仍为原零基字段；栏位显示再加一。
手动日期在 `J.int[6+aP]`，中断日期在 `J.int[11+aP]`；村名分别在 `J.string[2+aP]`／`[6+aP]`，
资金分别在 `[4+aP]`／`[8+aP]`。当前选择栏位存 `J.int[8]`。

标题页用目录日期 `-1` 判断没有数据，不先扫描游戏记录验证有效性。
“删除存档”在已见输入分支只将对应目录日期置 `-1` 后写系统，并未擦除对应游戏记录。
因此它是目录不可见化，不能作为敏感数据擦除保证。

2026-10-09补核[中断／手动目录生命周期](../verification/interrupt-directory-lifecycle/README.md)：
固定APK与Steam具名保存尾部只更新当前一条目录；普通继续／加载入口直接写的是选择槽8，
Steam `GameForm.Init` 的清零是 `int[16]=REVIEW`，不是中断日期11／12。
所核直接路径不支持“读中断后删除”“手动保存清中断”或“清全部目录”；此结论不扩展为全程序间接调用、异常／迁移和单槽平台政策的否定证明。
Steam标题Update另有诊断下载分支把当前手动日期写300，不属于普通菜单保存，本次没有执行或认证其玩家可达性。
维护现有保存／隐藏只动所选目录的合同不变；六个具名方法的原字节身份、有限指令窗和可复算脚本均见专题。

`e.a()` 还有把旧 `openFileInput` 文件逐一迁入偏好字符串、提交后删除旧文件的路径；
运行时协调器首次初始化调用它。它不等于当前 APK 常规保存仍以 `save1.dat`／`save2.dat` 写文件。
未取得真实设备 XML，偏好文件的实际完整路径不在本批认证范围。

## 保存与载入时点

### 手动保存

主场景的保存命令及菜单保存命令均创建 `raw14`。
页面初始化显示“游戏保存中”，其更新先将 `ce=0` 改为 `1`，下一次更新调用 `av.e()`，
后者固定转 `a(false)`；完成／失败后 `ce=2`，等待确认返回。
不能在 UI 绘制回调、每帧或打开菜单时重复提交保存。

页面失败时显示 `保存失败【bG】` 和异常，附加至系统诊断字符串并截取最后 1024 字符，尝试再保存系统。
`bG` 是分区写入阶段诊断，不是持久化 schema 版本。

### 自动“中断数据”

日期推进先将当前 `P.int[4]` 留到 `[5]`，加本轮推进量；若结果达到 `10800`，
暂时将 `[4]` 恢复为旧值，执行 `a(true)`，再恢复新增值并开始周／月／年归一化与结算。
即保存的是本次跨周日历消费者之前的状态，不是跨月维护费和事件全部完成之后。
低层`work/construction-render-fallback/MainScene.java`的`b()`在`L29d`先执行共同世界更新，
`L2df`执行显示尾部及菜单门槛，`Leb0`才在scene0调用日期推进；`c(int)`中保存还早于`UserData.t++`。
所以该档是“本轮世界已推进、日历尚未推进”的轮内位置，没有保存调用阶段／框架剩余轮数。
即使另补随机状态，从完整帧入口恢复也可能重复AI或收费，不能把它直接包装成精确回放快照。
`10800` 是原逻辑进度边界，不擅自换算成秒，也不描述成仅“每月自动保存”。
保存程序先设 `P.int[15]=1`，手动和自动都如此。

已见 Android 生命周期 [IApplication.java](../work/decompiled/sources/kairo/android/ui/IApplication.java)
的 `onPause`／`onStop`／`onDestroy` 没有调用游戏保存，最后一项直接结束进程。
全游戏调用核对只找到日历的直接 `a(true)` 和手动 `e()->a(false)`。
因此不能宣称失焦、切后台或系统终止必然保存到最近一轮。

### Steam手动保存页的局部交叉

Steam `SubForm.Init` RVA `312460`在VA `10314BDF`以“ゲームセーブ中”及空按钮参数调用InitDialog；Update（`321990`）raw14入口为`10326427`。state0首轮在`103267C5`仅置1；下一轮state1在`103264A1`同步调用`AppData.SaveGame()`（RVA `264040`），后者于`1026404A`传false进入手动写器。没有选栏、覆盖询问或额外保存确认，目标是当前栏位；与APK `b/g:10635,11485`及`d/a:3958`一致。

正常返回于`103264A6–103264C5`显示保存完成并置state2；异常拼接saveLine及异常文本，追加系统诊断、超1024截尾，`10326757`再尝试SaveSystem，二次失败也进入state2。state2才由`10326458`检查软标签2／确认脉冲并在`10326473`Pop；`_draw`的`10356EB9–10356EC9`也只在state2绘制确认按钮。state0／1的该局部没有取消或确认提前关闭处理；结果确认只关页，不重复写档。raw14及无参保存wrapper没有直接随机／PlaySe调用，不能把这一局部结论扩大为全部平台后端零副作用。

原先写游戏记录再写系统目录，原写前置P15为1、失败不回滚；系统写器又可能吞异常，故原“保存完成”不保证两个记录均已成功。维护加强事务沿[独立存取](../prototype/PERSISTENCE.md)，不复制原失败半状态。普通档仍要求唯一稳定scene，直接从raw14调用`save_world()`合法拒绝；已实现应用桥只对真实菜单保存链准备严格稳定导出，live保留结果页。完整成功候选在文件发布前准备，发布后仅无抛出安装；文件未发布的失败才生成失败页，旧档与业务不动。没有放宽一般模态／输出／建设／计分的有效拒绝；原木框与单按钮局部计划见[保存皮肤](../ui/STEAM_SAVE_MENU.md#raw14保存页的局部皮肤)，研究窗口应用宿主已接显式研究根、当前栏保存与冷载，见[维护入口](../prototype/PERSISTENCE.md)；原框架全部退出产生者、完整字体／TextLayout及完整标题窗口仍待接。

### 设置返回的系统保存

设置12的返回同样是保存产生者，但只写系统。APK `b/g.java:11418–11423,11458–11464`先调用`d/a.d()`再退休页面；该函数仅序列化J至记录0。Steam SubForm.Update的VA10326D28／1032715E调用SaveSystem RVA264060，写sysSave_至RecordStore0／record0；非日文另刷新GameForm缓存，SubForm.Finish RVA1EDFA0本身没有保存。画质／速度在世界P12／P13、音量／方向在系统J3／J4／J13，故不能把设置返回解释为保存当前世界，也不能把返回当撤销。

菜单项、键盘／鼠标门控差异和说明页随机见[设置／说明合同](../ui/PAGES.md#设置12值所属与返回边界)。维护系统2尚不承载这些完整设置，世界虽保存通关镜像也不能替代系统J9跨局权威；后续须按明确持久／平台输出契约实现，不能塞进opaque后宣称已还原设置存取。本批只补来源，不改维护文件格式。

### 载入

标题页选择“从中断数据处开始”或“读取存档”；前者直接调用加载，后者经过继续／重新开始／删除菜单。
实际加载入口使用 `a(slot, use_interrupt)`，偏好记录索引仍为 `(use_interrupt?3:1)+slot`。
进入加载前先调用新局重置入口并更新当前栏位及系统记录，之后读 `P` 和各分区；成功切入主场景。
主场景初始化重建普通状态 `0`、菜单页和自己的临时向量，不恢复保存时原页面栈。
加载失败标题页清 `P` 并显示“读取失败”，不是回滚到载入前正在游玩的世界。

## 二进制层级与边界

### 记录外壳

写入顺序是 `P.a()` 容器字节→原游戏校验→前置 8 字节大端 long 校验值→共同 XOR→标准字母表 Base64→偏好字符串 `commit()`。
读取反向处理，空／不存在记录返回空字节；非空记录去掉 8 字节头并核对校验，失败抛游戏异常。
XOR 密钥由协调器初始化的 11 个 int 拆为 44 字节，拆字节按低位到高位；不来自随机流。
这是可逆格式处理，不是可靠的加密或认证。

校验不是标准 CRC-32：原表生成的多项式分支与标准 CRC 相反。
现有[归档工具](../tools/src/archive.cpp)的 `game_crc32` 已独立维护该差异，不能调用标准 `crc32` 冒充。
偏好 Base64 解码器支持 GZIP 头，但本 APK 的正常偏好写入不先 GZIP；不要替所有保存负载假定压缩。

### `k` 容器

每个容器开头写大端 `int32` 组数 `5`，随后每组依次写 `int32 tag`、`int32 count` 和组内容：

| tag | 内容 | 单项表示 |
| --- | --- | --- |
| 0 | 子容器数组 | `int32` 字节长度＋子容器字节 |
| 1 | int 数组 | 大端有符号 32 位 |
| 2 | long 数组 | 大端有符号 64 位 |
| 3 | 字符串数组 | `int32` 字节长度＋字符串字节；写端 `getBytes()`，没有显式记录字符集 |
| 4 | 原始字节数组分区 | `int32` 字节长度＋原始内容 |

游戏根 `P` 的默认形状是 1 子容器、16 int、3 long、1 string、25 字节分区；
系统根 `J` 默认是 0 子容器、16 int、4 long、12 string、4 字节分区。
游戏的资金在 `P.long[0]`，日历在 `P.int[1..5]`，村名在 `P.string[0]`。
`P.child[0].int` 在写前指向固定事件调用计数 `aM`。

基础流还使用大端 `int16`、单字节布尔值及 `float` 的 IEEE-754 原位 `int32` 编码；
三维向量为三个 float，不能把人物或摄像坐标保存为整数地图格。

这些类型读器会在请求长度不足时抛 EOF，但没有已见全局最大计数／负长度／剩余尾字节／重复 tag 严格验证。
容器对预先存在的 int／long 等数组读取输入全部项，仅写入目标长度以内；短输入保留默认尾部。
子容器循环则先索引原子容器再作范围判断，不能由此推导任意长度安全。
多个固定目录分区按已加载定义表长度循环，没有每条定义 ID 或分区内记录数；地图按已建地图大小循环。
因此目录版本、尺寸和向量有序性属于隐式依赖，不是通用可扩展文件协议。

不透明保留的实际粒度是已知tag内有长度的单项，例如整个`bytes[index]`；**组本身没有总字节长度**，
未知tag不能可靠跳过。分区内部又常无逐记录长度，未知字段也不能一概跳过。
字符串若尚未确认编码，可保留原字节，不能先用猜测编码解码再重编码后宣称原样往返。
本批手工86字节容器夹具验证了已知int改写后其余字段、字符串原字节和两个不透明分区不变，
并按维护策略拒绝截断／未知或重复tag／负count／尾字节／超预算；这不是原读器的严格性、真实游戏档或外壳兼容验收。

## 脚本、页面、动画与随机

### 延迟续体保留，页面执行栈不保留

[c/c.java](../work/decompiled/sources/c/c.java) 的续体只在脚本 opcode6 产生。
程序身份由当前目录引用匹配：普通固定事件 `0+index`、人气程序 `1000+index`、设施程序 `2000+index`；
保存下一条指令和等待值，重载后主场景逐项减等待，到零恢复 `P.int[9]` 并从原位置继续。
它不是当前 C++ 的全部立即执行调用栈、页面栈或一般回调根的原字节表示。

原 [kairo/android/a/b.java](../work/decompiled/sources/kairo/android/a/b.java) 的页面 `f384b` 没有保存入口，
25 分区写器也不写任何 `b.g`；`raw14` 自身不会被保存后重开。
当前输入、选中行、已打开详情／问答／征集页面、页面局部计数和一次性声音均不能宣称可精确续演。
如果已创建未关闭成果页，其领域奖励及任务状态可能已保存，而结果页本身没有；
必须据原实际触发范围另验是否会遗漏或重放，不能从“世界有存档”自动推得“任何页面可保存”。

### 世界动作和表现记录分别对待

人物控制 FIFO `m`、连续坐标 `n/o/p/q/r`、格／投影缓存 `s/t/u/v`、状态 `A` 和动作计数 `B` 等确实写入。
物体阶段、投射物计数也写入。因此行走／战斗／旅馆服务不全部重新起步。
但人物 `cd/ce` 等局部显示队列，以及协调器 `S/X/Y` 通知／浮标／延迟特效向量未在写器中保存，
新局重置入口明确将 `S/X/Y` 设为空。摄像只写三个向量，不保存所有跟随引用。
当前 C++ 的表现缓存保存政策应分别记录“原来源已保存”与“维护为了检查点保留”，不能一律删或一律序列化指针。

### 原随机 seed／游标不保存

共同游戏随机只有 [c/d.java](../work/decompiled/sources/c/d.java) 的 `private static Random r=new Random()`，
抽取为 `abs(nextInt()%bound)`。全生成源码搜索未见它的 setter、反射访问、Java 对象序列化或 seed 导出／恢复，
完整保存写器也没有它的分区。

结论限定到这个固定 APK：同一进程载入会延用当前 `Random` 的已消费状态；
冷启动由 Java 默认构造生成新的 seed，不能保证从同一存档继续得到同一条随机轨迹。
原标题动画也消费共同随机，所以“先停在标题多久”可能影响后续流。
`Random` 自身的内部状态不是已见保存在 `UserData` 某个未命名 int 中的字段。

维护 C++ 当前有明确 Java48 seed／原始磁带和消费游标。为了可复现测试保存该状态是有价值的独立策略，
但不得标成原 APK 已保存 seed，更不能用原默认 seed 未知来填固定 `1` 后宣称原版复演。

## 版本与失败策略

系统默认 `J.int[0]=108`，启动加载器遇到小于108会写回108。
此处只见系统版本标记更新；游戏根默认 `P.int[0]=0`，本次没有找到载入游戏前对 `P` schema 版本严格相等的检查。
网络响应“版本大于108”的检查是客户端／网络认证路径，不是本地存档 schema 校验。
不由这些字面量推导跨版本存档普遍兼容，更不复制原修复大分支作为维护旧档迁移功能。

原存取风险必须与维护策略分开：

- 偏好 `commit()` 返回失败会抛异常，但游戏记录与系统目录分两次提交，没有跨记录原子事务。
  游戏已提交、系统未提交时目录可能落后；系统写器 `d()` 自己捕获异常并打印，手动页不一定收到该错误。
- 序列化先修改 `P` 标志和字节分区，保存失败没有已见候选快照回滚。
- 加载先重置当前世界和系统选择，再逐分区修改；缺引用在多个小方法中置空／省略，不全是加载错误。
- 外壳校验只检测字节改动；不会检查业务 UID 唯一性、地图占地、目录 ID、重复成员、负尺寸或资源配额。
- 原格式字段宽度和目录隐式长度构成约束，不能因 C++ 容器支持更大规模就声称原格式也支持。

`RecordStore.Setup 0x728780`创建media4／security=true的根Storage。不能根据形参或方法名猜媒介。
`Storage.GetFolder 0x729F80`的USE_STEAM分支返回`Path.GetDirectoryName(Application.dataPath)+"/saves/"+SteamID`，
构造器`0x72B410`还组合Config.ROOT_FOLDER；逻辑记录名为`0001`—`0004`，不得擅加`.dat`。
上述初批只定位到Config静态默认值；后续已闭合MyConfig覆盖链及实际目录，见下节。不再将初始USE_STEAM=0当作最终运行配置。

## 原版恢复合同：缺失引用、冒泡与日历（2026-10-07）

本轮继续静态交叉和已授权副本最小计数。原游戏窗口通道两次返回native pipe不可用，未启动原游戏、未生成受控新档，
以下区分方法事实与样本条件推论；静态批记录以当时范围为准，后续真实恢复端点统一见下文实样矩阵。
维护格式与原版合同分开，不能由Steam观察直接改变APK规则。

### 缺失UID与遭遇消失状态

Steam `MAA.Deserialize2`委托`MAAGroup.Deserialize2`重建两侧名单：逐个保存UID线性查找当前人物／怪物集合，
找到才追加，找不到就继续处理下一项；不会补建替代实体，也不会仅因缺一项而拒绝全档。
保存名单中重复UID按出现次数追加同一对象引用，不自动去重。恢复方法不改组状态、计数，也不直接删除遭遇。
元数据的泛型实例与实际Vector调用已交叉，不能把共享机器码地址的其它类型别名当作此方法语义。

| 既有样本的遭遇163 | 0001手动 | 0003中断 |
| --- | --- | --- |
| 保存的怪物名单 | UID0出现3次，当前怪物集合仅UID1 | UID0出现3次，当前怪物集合含UID0、1 |
| 按所核二阶段方法得到的名单 | 3人／0怪；三次未匹配均跳过 | 3人／3项同一怪物引用；不是3个独立怪物 |
| 遭遇自身原k／l | state=1（消失中），counter=78 | state=0（普通），counter=131 |
| 组原group.d／e／f／h | 0／28／0／80 | 0／51／0／80 |

遭遇自身状态与战斗组状态是不同字段；先前读取的遭遇d／e=1／0不能代作组state／counter。
`MAA.Update`对消失中分支先增加自身counter，再判断100门槛，不调用组Update；
所以在无其它状态干预且继续获准调用的条件下，0001这条遭遇在第22次该方法调用返回完成信号。
外层`UserData.Update`在VA `0x102EED1D`取得该返回值，true时于`0x102EED65`按当前索引从活跃遭遇列表移除，
随后逆序继续；false则跳过移除。这只证明离开活跃列表，不等于所有外部引用已经释放。
这不是22个可见帧或22秒，也不是“怪名单为空导致立即删遭遇”；该档已处于原消失流程。

普通状态仍可能因地图／围栏等资格提前转消失；只有实际到达组Update，才推进其counter。
组Update自身不因名为STATE_NONE的state值就停止；回合门槛检查后，任一侧空才进入清标志／清名单流程。
不能把普通状态样本机械预测为固定时间内走某条战斗分支。
来源与全部条件见[Steam引用恢复](../work/restore-behavior-analysis/steam-references/REFERENCES.md)。

### p不是全部业务效果

`p`归属每个设施实例，是临时表现队列，不是建筑目录、施工中的建筑集合或施工进度本身。
每个条目为[提示类型,消费计数]；施工完成提示只是其中一种，邻接变化也能产生其它类型。
施工资格／进度由独立状态与计数字段保存，所以加载丢弃p不意味着删除建筑或取消施工。
APK `c/m.c(int)`按种类去重并追加`[种类,0]`，`d()`只推进队首计数，到对应F阈值移除；绘制方法读取该队首。
类型0阈值44，类型1—6为43，类型7为60，均为调用计数。邻接属性差值产生类型1—6时，属性计算已经完成。
Steam `Tenant.Update`／`Update_fukidashi`也先判队列是否为空，`RegistFukidashi`新建条目计数为0。
空p不会由这个首个消费者自动重放旧冒泡；后续真实产生点可新增，这不等于恢复旧条目。
它不同于共享道具改良、实例y计数、k探索记录或全局延迟脚本；不能由“丢p”推出物品回退、奖励重发或所有待执行效果丢失。

最初两份实样的39设施均state=1，p总0、k行14，当时没有非空p前提；后续已取得并实际加载非空输入，见下文实样矩阵。
来源和最小诊断见[设施表现恢复边界](../work/restore-behavior-analysis/EFFECTS.md)。维护精确回放保留p及输出的政策不因此改变。

### 回到完整更新入口，不是回到原保存调用之后

APK标题加载成功后切主场景，场景初始化调用a(0)，重置scene及局部计数；框架初始化分支先返回，之后才调用更新。
已保存的业务UserData.t与场景计数、未保存的外层计数分别对待，不能一概清零或宣称全部恢复。
正常更新先处理脚本资格，再共同世界更新，再处理显示／菜单，最后scene仍为0且确实到达日历调用点才推进日期。

固定APK传入日历的参数是协调器`d.a.R=43200/(80×20)=27`，不是MainScene同名实例字段12。
在正常加载后给定time=oldtime=10773、无阻断且保存调用返回的条件下，首个**有资格日历调用**加27，
达到10800时临时还原旧10773再调用中断保存，返回后才t++、周归一化及周消费者。下个有资格日历调用通常推进0→27，
并非每轮连续保存；双轮、开页和脚本可能改变同一外层更新最终到达的位置。
这是把样本数值作为输入的APK条件推论，不是运行APK读过Steam档，也不等于点击加载立即跨周。

Steam对应链已经独立核到`TitleForm.ContinueGame→LoadGame→ChangeCurrentForm`、`GameForm.Init→ChangeState(0)`；
普通`GameForm._update`先调用UserData.Update，尾部才`ProgressTime(FRAME_TIME1,frameCount)`。
ProgressTime明确先oldtime=time再试加add，达到10800时暂回旧time调用SaveGame(true)，恢复试加值后才monthCnt++及周／月／年消费者。
后续无窗口补证已核`AppData..cctor`：VA `0x10268FE8`写DAY_SECOND1=80，
`0x10268FF7`—`0x10269008`按43200/(80×20)得FRAME_TIME1=27。
这是Steam默认初始化的直接证据；全部运行期赋值仍未闭合，不把27无条件套到全部配置。

原保存位置包含已推进世界与未推进日历，但没有执行游标；读档后重新进入完整更新链，因而不等于精确尾段重放。
实体动作、资金等已经持久化，不能由多一次世界函数调用就断言同一笔收费或奖励必然重复；
原周消费者尚未进入跨周中断档，也不能把随后进入该边界直接叫作重复结算。

### 两项不能忽略的Steam加载边界

- `KairoService.SaveAll`在save非null时还能依次调用SaveGame(true)、SaveGame(false)、SaveSystem。其全部生命周期触发器未闭合，

## Steam退出与文件失败的局部合同

<a id="steam退出委托与文件失败语义续批"></a>

新增13个明确方法／5,808字节及精确metadata槽解析，完整坐标见[生命周期证据](../work/steam-save-lifecycle-analysis/README.md)。
`Main.OnDestroy`读取的槽`0x110E88B0`实际为`AppPlugin.<>c.<Finish>b__4_0`，MethodDef32292、RVA0x1C9750，共享实现为`ret 0`。
这闭合了该特定委托，它不执行SaveAll；`wait=true`只等待该委托，不是文件刷新保证。
退出还有前置`FormManagerBase.ProcessEvent(Exit=3)`、后置另一`KairoPlugin.Finish`，不能由空委托断言整个退出链不保存。
另一插件委托已核Close／Dispose／清引用；本批确认对象为语言对话框，不是游戏主窗口。
`PlayerPrefs.Save`保存显示配置，不等于游戏0001／0003落盘。
SaveAll已证true→false→system的顺序保留，完整生命周期上游仍未认证。

后续[保存分派证据](../work/save-dispatch-closure/README.md)新增12个明确入口／10,304字节：
管理器`OnProcessEvent`虚槽11为`ret 0`，表单`ProcessEvent`虚槽29（0x1D）返回false；
已登记`FormManager`、`GameForm`、`TitleForm`和`MyFormBase`没有对应业务覆盖。
因此所核Exit继承分派路径不执行SaveAll；这是具体接收者的局部排除，不代表整个退出绝不保存。

游戏内结束确认先调用`RemoveAllForms`，写表单`formProcMode_=4`；框架退休调度成功后移出列表。
通用帮助器`0x10097EC0`未全部解析，不将移出列表当作所有引用释放。
已登记三个游戏表单的`Finish`均无保存调用；`TerminateCheck`满足条件才进入`Terminate`。
`Terminate`在VA `0x1078DA42..0x1078DA51`调用KairoBase槽12 `Finish`（类指针偏移0x11C），
不是槽18 `SaveAll`（偏移0x14C）。已登记KairoService的Finish尾调只置start=false的基础Finish。
上述排除仍成立；随后沿框架运行尾段核到槽18的正向条件，见下一节。

普通Storage.Write媒介4路径直接调用`File.WriteAllBytes`；本样本`InternalWriteAllBytes`在VA0x109E8785以
`FileMode.Create(2)`、Write(2)、FileShare.Read(1)对**原目标路径**构造FileStream，再Write并释放。
异常展开也释放并重新抛出，所核路径没有候选临时文件替换或旧字节恢复步骤；下层OS适配及所有异常类型未全部闭合。
所以“成功创建／截断后再写失败可能无法保留旧完整档”是代码顺序风险推断，不是已在用户档实测损坏。
游戏记录与系统目录逐次写入，不能称多文件统一事务；本地流释放也不认证断电耐久或Steam云已提交。

`Storage.Write`的匹配异常槽VA `0x11103730`已精确解码为`System.UnauthorizedAccessException`
（usage编码0x20005CB3、TypeIndex11865、TypeDef1372）。所核分支只对该匹配类型构造
`NotPermitException(type0, message, inner)`并抛出，其他异常再抛；不泛称所有I/O失败都由该包装处理。
本批未制造权限拒绝、磁盘满或用户档损坏，也未认证完整界面异常传播。

维护AVRSAVE1继续采用候选校验、临时文件、回读和替换的独立策略，不因原程序直接写目标而降低校验或失败保护。
菜单保存的state0→1→SaveGame→2与确认仅关提示见[Steam交互合同](../ui/STEAM_INTERACTIONS.md)，界面成功提示与底层保证分别登记。

### Steam预留保存的正向上游

2026-10-07只读同身份Steam2.56的机器码／metadata，新增15个明确方法20,000字节、3个直接调用窗口530字节；
完整来源、坐标、66项核验及未决见[本批证据](../work/saveall-upstream/README.md)。没有启动游戏、读取实时档或故障注入。
这是Steam独立事实，不将APK暂停／退出改判为同样行为。

`FormManagerBase._execute`先取得`KairoBase.GetInstance`，成功尾段VA `0x107EA7D7`调用辅助`0x107E0210`。
辅助要求对象非null、`reserveSaveEnable`为真、`reserveSave`非零；先复制预留值并清原值，再分派：
值1→槽17 `Save`，值2→槽18 `SaveAll`；其它非零值在本处清除但不执行这两种保存。
虚分派帮助器的实际指针公式为类偏移`0xBC+slot*8`，槽18对应`0x14C`；不是由方法名称猜调用。
`SetReserveSave(all)`取`all+1`并仅提升请求等级，false请求不能覆盖已有值2；使能关闭时本辅助不消费请求。

`KairoService.GetInstance`明确登记同一`KairoBase.instance_`；基础取实例入口无服务时可以返回dummy，不能默认它执行业务。
服务已注册且`apdat_.save_`非null时，`SaveAll`依次`SaveGame(true)→SaveGame(false)→SaveSystem`。
三个记录依次写入，和直接目标Create路径一致，没有跨文件回滚保证。

辅助匹配异常槽确认为`System.Exception`；局部最多尝试3次，每次匹配失败传入线程等待500毫秒，包括第三次失败。
预留在首次保存前已清零，最终失败不恢复；已经部分写入的保存可能重试，不保证幂等或旧档恢复。
局部临时异常槽在重试后退休，不据此宣称全部世界引用已退休；未匹配异常的路径重新抛出。

原先Close候选的对象是`KairoPlugin.languageDialogWindows_`。其已登记构造仅订阅Click／CheckedChanged／SizeChanged；
本样本`Form.Close`是交给runtime帮助器的48字节stub，不能补成标准.NET主窗口Closing／Closed事件链。
因此本批闭合的是运行尾段的预留保存分派；全部请求产生入口、停止运行后是否有消费机会、
OS关闭／暂停／强制终止是否触发保存仍未知。已有五处Billing setter记录不是完整入口清单或玩家动态认证。
