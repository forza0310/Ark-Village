## 推荐实施边界

1. 先列出正常场景、菜单/暂停、月报展示、跳过输入和状态 3 的入口/出口条件，
   对关键分支保留低层标签和消费者来源。未知路径显式标记，不猜测完整调度。
2. 日历与月报是两个关联时钟：分别维护归一化的年/月/子周期/剩余量、月内调用计数，
   以及展示状态/计数。主场景调用资格由经过核实的输入投影表达，不照搬巨型 UI 状态机。
3. 独立示例采用标准库状态与显式输入，输出有序事件及快照触发点；先覆盖可认证的正常路径。
   一批输入按候选副本验证后提交；非法输入/溢出不留下部分状态。失败保护是示例设计，
   不声称原作 Java 数值运算或保存行为具有相同保护。
4. 不直接复用现有 PeriodAccounting 的“准备报表即封账”来代表原作日历：原作准备后仍可能更新人物。
   报表快照与月度统计的关系必须单独核实，保持既有账本接口不变；未知期末归属不得靠冻结猜测。
5. 费用金额、人物和设施资格沿用已有消费者证据；测试输入可以是夹具，但需注明来源等级。
   本阶段只研究结算调度，不扩展完整职业费用表、怪物奖励表或全部设施效果。
6. 不新增任务/战斗/存档实现，不修改 R2 原型或产品，不恢复完整 UI 绘制，不复制反编译实现。
   状态 3 若无法闭合，保留明确的未实现路径，不虚构入口，也不声称完整月报已复刻。
