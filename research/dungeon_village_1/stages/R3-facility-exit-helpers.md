## 方案与取舍

采用 A：两个独立纯函数分别准备共享使用累计与普通商店满足度候选，由调用者保留身份并提交。
不采用 B（完成后无条件升级/全属性加值），这与已定位的提示标记和分类分支不同；不采用 C（搬运
整个退出状态机），其装备、动画、同行和脚本尚未解释。本方案不替代完整复刻目标。

1. 定义进度包括等级 1–5、有符号 int32 非负使用累计和原升级提示 L。每次有效退出累计加 1，
   再按既有经营函数计算升级阈值；满足门槛只将提示置 true，其他情况下保留已有提示，不清零/升等级。
2. 使用溢出、无效 ID/等级/负计数/非法端点拒绝，无部分候选；宽整数不复刻 Java 回绕。
   不把同一实例的统计存入共享进度；定义 ID 可以为 0，实例 ID 不混入函数。
3. 满足度 helper 输入角色/实例/定义身份、C（0–100）、职业门槛端点、已派生实例品质和外部 0–9 票号。
   整数插值向零截断，加 ticket-5 后与品质比较，等号算成功；不内置 RNG 或声称均匀原作随机。
4. 成功请求 C 加 1 并封顶到 100，同时请求人气 +1；失败仍返回人气 0 请求。返回请求与实际 C 差值
   分开，C 已为 100 时成功仍请求 +1 人气。提示标志 false、reason 0、延迟逻辑计数 10。
5. 函数不自动检查角色分类或执行完整退出：调用点只在类别 1 且细分类非 1/4/5 的分支；品质必须是
   实例槽 1（含邻接/封顶），不能把定义基础值或魅力代入。人气请求不是即时金币/村子点数。
6. 不实现升级 UI、完整人气队列、状态恢复、属性 opcode 19 或装备效果；不接入有限原型。

## 验收

- 等级 1–5、阈值前/等于/之后、第五端点零、原提示保持、共享累计/输入不变和 int32 最大值拒绝。
- C=0/100、所有随机票号、等号/严格大于、负品质/降序门槛、整数截断、极值宽算术。
- 固定种子独立标量差分、原表阈值夹具/经营派生品质到候选组合、成功/失败/封顶人气请求区分。
- 示例三套与原型三套当前构建/CTest、格式/中文链接、原件只读、本地 Git 检查点与进程收尾。
